# BARNEY-NANO — компактный университетский помощник

BARNEY-NANO — экспериментальная компактная модель для университетских сценариев. Она не заменяет backend, Neon или инструменты приложения. Модель формирует язык и интерпретирует намерения; актуальное расписание, аудитории, профили, группы и другие данные по-прежнему берутся только из существующего backend.

## Выбранная стратегия

- Учитель: локальная LFM3 через Ollama.
- Ученик: HuggingFaceTB/SmolLM2-360M-Instruct (около 360 млн параметров).
- Обучение: supervised fine-tuning LoRA на проверенных ответах, сгенерированных LFM3 и одобренных человеком.
- Экспорт: объединённый checkpoint → GGUF → Q4_K_M.
- Первый deployment target: экспериментальный отдельный inference-процесс. Существующий Telegram backend, Neon и Mini App не заменять до успешного теста.

Почему не обучаем 300M с нуля: случайно инициализированная модель такого размера не имеет базовых языковых знаний. Ученик на основе предварительно обученной модели 360M сохраняет языковые способности исходной модели, а дистилляция адаптирует её к русскоязычным университетским задачам. Это не гарантирует качество LFM3. Исходная SmolLM2 в основном ориентирована на английский, поэтому качество русского языка — отдельный критерий benchmark, а не предположение.

## Важное ограничение Render Free

Файл GGUF Q4_K_M для исходной SmolLM2-360M-Instruct занимает ориентировочно 271 МБ в опубликованной квантизации. После дообучения размер может немного отличаться. Но размер файла — не требуемая RAM: llama.cpp дополнительно использует память под runtime, контекст, KV cache, буферы и сам backend.

Render Free предоставляет ограниченную память (512 MB для Free Web Service), поэтому нельзя обещать, что модель запустится вместе с Rust backend в одном сервисе. Даже отдельный Free inference service может упираться в лимит памяти, холодный старт и CPU-производительность. Реальное решение принимается только после замера RSS, времени первого токена и скорости генерации на Render. Если не проходит — не ломать основной backend и не переключать пользователей; уменьшить контекст/квантизацию или признать, что нужен больший тариф/внешний runtime.

## Подготовка Windows

1. Установить Python 3.11 x64, Git for Windows и Ollama.
2. Скачать базовую модель-учителя в Ollama и проверить ollama list. Имя по умолчанию — lfm3.
3. Установить PyTorch с CUDA в отдельное окружение .venv-barney-nano через официальный селектор: https://pytorch.org/get-started/locally/
4. Распаковать репозиторий в папку проекта.
5. Запустить scripts\\barney_nano\\BARNEY_NANO.bat.
6. Выбрать [1] First-time setup, затем [2] Hardware and dependencies check.
7. Убедиться, что CUDA видит RTX 4050. Не продолжать, если CUDA недоступна.

## Цикл дистилляции

1. Запустить [3] Generate candidates with LFM3 teacher. Начать с 20–50 примеров.
2. Проверить каждую пару через [4] Review / approve dataset. Исправлять неточные ответы, отклонять сомнительные. Не обучать на сырых непроверенных диалогах.
3. Собирать разнообразные университетские сценарии: пары и расписание, дедлайны, аудитории, учебные дисциплины, программирование, научная работа, студенческие сервисы, университетские сообщества, безопасность и корректный отказ при отсутствии данных.
4. Для первого smoke test достаточно 30 одобренных примеров; для осмысленной специализации ориентир — сотни и затем тысячи разнообразных, качественных примеров.
5. Запустить [5] Train BARNEY-NANO. Стартовый профиль: LoRA rank 8, batch 1, gradient accumulation 16, context 512, 3 эпохи. Это стартовая настройка, не гарантия отсутствия OOM.
6. Запустить [6] Evaluate trained adapter. Проверить ответы на тестовых запросах и сравнить с базовой моделью. Не использовать обучающие примеры как benchmark.
7. Только после проверки запускать [7] Merge adapter for GGUF export.

## Что должно оставаться вне весов модели

Не зашивать в модель изменяемые сведения о конкретных студентах, преподавателях, расписании, оценках, аудиториях и событиях. Они устаревают и должны поступать из backend. Не включать в датасет Telegram ID, имена, телефоны, адреса, приватные переписки, пароли, API-ключи и другие секреты. Пользовательские действия (изменение профиля, запись на мероприятие, изменение настроек) выполняются только существующими backend-инструментами с проверкой прав.

## Следующий этап: GGUF и deployment

После локального benchmark:
1. Установить актуальную сборку llama.cpp.
2. Конвертировать training/barney-nano-merged через convert_hf_to_gguf.py.
3. Квантизировать Q4_K_M (если доступен соответствующий llama-quantize.exe).
4. Проверить модель локально через llama-server.
5. Замерить память и скорость на Render в отдельном экспериментальном сервисе, не меняя основной Telegram backend.
6. Только если тест пройден, добавить конфигурацию URL/ключа в Render и переключить AI-клиент backend. Neon и Mini App не требуют миграции.
